# Lab: Adding New Relic APM Monitoring to the Student Management Stack

This lab walks through adding New Relic Application Performance Monitoring
(APM) to the Phase 11 stack (two frontends, gateway, three microservices,
three Postgres databases, Splunk log monitoring), step by step, starting
from a working Phase 11 checkout. Application code doesn't change — this
is a Docker/config-level addition, same spirit as the Splunk lab in
[`Splunk-Lab-Manual.md`](./Splunk-Lab-Manual.md).

By the end you will have a real New Relic account, a license key wired
into four Java services, and live transaction traces in New Relic's UI
generated by your own traffic through the app.

**Estimated time:** 30–40 minutes (most of it is New Relic account setup
and waiting for data to appear, not Docker work).

## Prerequisites

- Docker and Docker Compose v2
- A working Phase 11 checkout of this project (or Phase 12, if you're
  redoing this lab from a checkout that already has it)
- An email address to sign up for New Relic's free tier (no credit card
  required for the free tier at the time of writing)

## Step 1 — Copy the project to a new phase directory

```bash
rsync -a --exclude='target' --exclude='__pycache__' --exclude='node_modules' --exclude='dist' \
  Phase-11/ Phase-12/
cd Phase-12
```

## Step 2 — Create a New Relic account and get a license key

1. Go to New Relic's signup page and create a free account.
2. Once logged in, click your account name/avatar (top right) → **API
   keys**.
3. You'll see a table of keys. Look for one of type **License key**
   (sometimes labeled "Ingest - License"). If none exists yet, use the
   "Create a key" button and pick that type.
4. Copy the key's value — a long alphanumeric string. This is the only
   credential this lab needs.

**Don't confuse this with the "User key"** on the same page — that one is
for New Relic's own API automation (NerdGraph, custom dashboards) and
isn't used anywhere in this lab.

If you're doing this lab as part of a team/class that already has a
shared New Relic account, ask whoever administers it for a license key
instead of creating a personal account — everyone's services can report
under the same key.

## Step 3 — Understand what the agent needs, before writing any config

The New Relic Java agent is a **javaagent** — a jar loaded into the JVM at
startup via `-javaagent:/path/to/newrelic.jar`, not a separate process or
container. It instruments the running application from inside the same
JVM and sends data (transaction traces, response times, errors) directly
to New Relic's cloud over outbound HTTPS. Nothing needs to be reachable
*into* your host for this to work — that's the whole reason this approach
needed no privileged container, unlike host/container-level metrics
collection (see the callout at the end of this lab).

Two things the agent needs to find at startup:

- **The agent jar and a config file** (`newrelic.yml`) — baked into the
  Docker image at build time.
- **A license key and app name** — supplied at container-run time via
  environment variables (`NEW_RELIC_LICENSE_KEY`, `NEW_RELIC_APP_NAME`),
  *not* baked into the image, since the image is the same for every
  environment but the key is a secret that shouldn't be committed.

## Step 4 — Add the agent to each service's Docker image

Do this for **all four** Java services: `student-service`,
`course-service`, `enrollment-service`, `gateway-service`. Each needs the
same three additions.

### 4a. A `newrelic.yml` in the service directory

```yaml
# <service>/newrelic.yml
common: &default_settings
  license_key: 'REPLACE_WITH_NEW_RELIC_LICENSE_KEY'
  agent_enabled: true
  distributed_tracing:
    enabled: true
  application_logging:
    forwarding:
      enabled: true
  log_file_name: STDOUT

production:
  <<: *default_settings
  app_name: stu-mgmt-student-service   # change per service, see table below
```

| Service | `app_name` to use |
|---|---|
| `student-service` | `stu-mgmt-student-service` |
| `course-service` | `stu-mgmt-course-service` |
| `enrollment-service` | `stu-mgmt-enrollment-service` |
| `gateway-service` | `stu-mgmt-gateway-service` |

The `license_key` placeholder value never actually gets used — see Step 5.
It's there because the agent still expects a well-formed yml file to
exist even though every value in it gets overridden at runtime.

### 4b. A `docker-entrypoint.sh` in the service directory

```sh
#!/bin/sh
set -eu

# The agent is only attached if a real license key was supplied at
# runtime. Without this check, running the stack with no
# NEW_RELIC_LICENSE_KEY set would still load the agent, which then fails
# to connect and adds startup noise for a monitoring backend nobody
# configured. With the check, an unconfigured stack behaves exactly as it
# did before this lab.
JAVA_OPTS="${JAVA_OPTS:-}"
if [ -n "${NEW_RELIC_LICENSE_KEY:-}" ]; then
  JAVA_OPTS="$JAVA_OPTS -javaagent:/app/newrelic/newrelic.jar"
fi

exec java $JAVA_OPTS -jar app.jar
```

Make it executable: `chmod +x <service>/docker-entrypoint.sh`.

### 4c. Update the service's `Dockerfile`

Change the final stage from this:

```dockerfile
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /build/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

to this:

```dockerfile
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# New Relic Java agent (APM). Downloaded at build time from New Relic's
# public download host - no account/key needed to fetch it, only to
# actually report data once running.
RUN apk add --no-cache curl unzip \
    && curl -sSL -o /tmp/newrelic.zip https://download.newrelic.com/newrelic/java-agent/newrelic-agent/current/newrelic-java.zip \
    && unzip -q /tmp/newrelic.zip -d /app \
    && rm /tmp/newrelic.zip \
    && apk del curl unzip

COPY --from=build /build/target/*.jar app.jar
COPY newrelic.yml /app/newrelic/newrelic.yml
COPY docker-entrypoint.sh /docker-entrypoint.sh
RUN chmod +x /docker-entrypoint.sh

EXPOSE 8080
ENTRYPOINT ["/docker-entrypoint.sh"]
```

The build-stage (Maven compile) above this is unchanged — only the final
runtime stage changes.

## Step 5 — Wire the key into `docker-compose.yml`

For each of the four services, add two environment variables to their
existing `environment:` block:

```yaml
  student-service:
    build: ./student-service
    environment:
      DB_HOST: student-db
      # ...existing DB_* vars...
      NEW_RELIC_LICENSE_KEY: ${NEW_RELIC_LICENSE_KEY:-}
      NEW_RELIC_APP_NAME: stu-mgmt-student-service
```

Repeat for `course-service`, `enrollment-service`, and `gateway`, each
with its own `NEW_RELIC_APP_NAME` from the table in Step 4a.

**Why `${NEW_RELIC_LICENSE_KEY:-}`, not the literal key:** this reads the
key from your shell environment or a `.env` file at compose time, so the
actual key value never gets typed into `docker-compose.yml` (which is
typically committed to git). The trailing `:-` with nothing after it
means "default to an empty string if unset" — that's what lets the whole
stack still start with monitoring off if nobody's configured a key yet.

## Step 6 — Put your key where compose can find it

Create a `.env` file next to `docker-compose.yml` (this file should be
gitignored — check before committing anything else in this directory):

```bash
# Phase-12/.env
NEW_RELIC_LICENSE_KEY=your-real-license-key-from-step-2
```

Docker Compose reads `.env` automatically for any `${VAR}` reference in
`docker-compose.yml` — no extra flag needed.

## Step 7 — Build and start the stack

```bash
docker compose up -d --build
```

Splunk's first-boot healthcheck (carried over from Phase 10) still gates
everything else, so give it 30–60 seconds. Once up:

```bash
docker compose ps
```

All ten containers (2 frontends, gateway, 3 services, 3 databases,
splunk) should show `Up`.

## Step 8 — Confirm the agent actually attached and connected

Don't just trust that it's configured — check the logs for the real
handshake:

```bash
docker logs <student-service-container-name> 2>&1 | grep -i newrelic
```

You're looking for two specific lines, which appear about 20–40 seconds
after the container starts (they show up after the agent's first harvest
cycle, not immediately at boot):

```text
Agent 1@<host>/stu-mgmt-student-service connected to collector.newrelic.com:443
Reporting to: https://one.newrelic.com/redirect/entity/...
```

If you see `New Relic Agent v9.x.x has started` but never the
`connected to collector` / `Reporting to` lines even after a minute or
two, the agent attached but failed to authenticate — see Troubleshooting
below.

Repeat this check for `course-service`, `enrollment-service`, and
`gateway` — all four should show the same pattern with their own
`stu-mgmt-*` app name.

## Step 9 — Generate real traffic, then find it in New Relic

An idle connection with nothing to report isn't a very satisfying demo.
Create something through the app so there's an actual transaction trace
waiting:

```bash
curl -s -X POST http://localhost:9000/api/students \
  -H "Content-Type: application/json" \
  -d '{"name":"New Relic Test","email":"newrelic.test@example.com"}'

curl -s http://localhost:9000/api/students
```

Then:

1. Log into [one.newrelic.com](https://one.newrelic.com).
2. Open **APM & Services** in the left nav. You should see all four
   `stu-mgmt-*` apps listed (give it a minute if they're not there yet).
3. Click into `stu-mgmt-student-service`. You'll see the `POST
   /api/students` and `GET /api/students` transactions you just
   triggered, with response times and a full trace.
4. Click into `stu-mgmt-enrollment-service` and enroll a student
   (`POST /api/enrollments?studentId=1&courseId=1`, after creating a
   course too) — because `enrollment-service` calls `student-service` and
   `course-service` over HTTP to do this, New Relic's distributed tracing
   shows that whole cross-service call chain as one connected trace, not
   three separate unrelated ones.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| No `newrelic` lines at all in a service's logs | `NEW_RELIC_LICENSE_KEY` wasn't set when the container started | Check `.env` exists and is in the same directory as `docker-compose.yml`; `docker compose config` will show you the resolved env value per service (careful: this prints the real key) |
| `New Relic Agent v9.x.x has started` appears, but `connected to collector` never does | Usually an invalid or mistyped key, or the container has no outbound internet access | Double check the key value (no extra whitespace/quotes in `.env`); confirm the container can reach `collector.newrelic.com:443` (`docker exec <container> sh -c "wget -q -O- https://collector.newrelic.com || echo unreachable"`) |
| Build fails downloading `newrelic-java.zip` | No internet access at build time, or New Relic's download host is temporarily unreachable | Retry the build; this download happens fresh every image build (it isn't cached across builds unless your Docker layer cache is warm) |
| App container that never had `NEW_RELIC_LICENSE_KEY` set now shows agent output after you added a key | Expected — this is exactly the conditional entrypoint from Step 4b working as intended | Not a bug; this confirms the mechanism |
| Apps show up in New Relic but with generic-looking names like `My Application` | `NEW_RELIC_APP_NAME` wasn't set, or the yml's placeholder `app_name` wasn't overridden | Confirm the env var is set per-service in `docker-compose.yml` exactly as in Step 5 |

## A note on what this lab deliberately leaves out

New Relic also offers an **Infrastructure agent** for host/container-level
CPU, memory, disk, and network — data the APM agent above doesn't cover
at all (APM only sees inside the JVM it's instrumenting). That agent
needs a genuinely different, more invasive setup: a privileged container
with the host's PID namespace, host networking, and Docker-socket access,
because collecting *that* kind of data requires visibility into the whole
host, not just one JVM process — being cloud-reporting like APM doesn't
remove that requirement.

This lab (and this phase) deliberately stops at APM. If host/container
metrics are wanted later, that's worth treating as its own explicit
decision with its own tradeoff discussion, not a "might as well, we're
already doing New Relic" addition — see the note in
[`New-Relic-Monitoring.md`](./New-Relic-Monitoring.md) §5 for the full
reasoning.
